# Native Streamable HTTP and Hermes Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a native loopback Streamable HTTP MCP endpoint at `127.0.0.1:9090/mcp`, preserve stdio compatibility, add HomeClaw's Hermes integration UI, and migrate the local Hermes entry away from `supergateway` after live verification.

**Architecture:** Adapt the existing Swift/NIO MCP HTTP implementation into the compiled Catalyst app. The HTTP layer owns NIO framing, loopback/Host/Origin policy, content negotiation, stateful session lifecycle, and SSE; it delegates tool registration and HomeKit calls to the existing `MCP.Server`/`ToolHandlers` path. Hermes connects through its native `mcp_servers.<name>.url` configuration, while the Node stdio wrapper remains unchanged.

**Tech Stack:** Swift 6.2, Swift MCP SDK, SwiftNIO HTTP1/Posix, Mac Catalyst, SwiftUI, XcodeGen, Hermes native MCP client, Python MCP Streamable HTTP client for live verification.

**Spec:** `docs/superpowers/specs/2026-08-31-native-streamable-http-hermes-design.md`

## Global Constraints

- The native endpoint binds only to loopback; no remote bind or bearer-token mode is added.
- The default HTTP port is fixed at `9090`; a test/developer override may change only the port.
- Existing stdio, Claude Desktop, Claude Code, and OpenClaw integrations remain compatible.
- HTTP must reuse the existing MCP tool definitions and HomeKit dispatch; no HTTP-only tools or mutation semantics.
- Host/Origin validation must reject DNS-rebinding/public origins.
- The transport must not log request bodies, credentials, authenticated URLs, or HomeKit payloads.
- Hermes configuration is changed with Hermes-supported tooling, not by hand-editing `~/.hermes/config.yaml`.
- No live credentials are placed in tests, logs, generated snippets, commits, or command output.
- Follow strict TDD: each production behavior starts with a focused failing test, then minimal implementation, then green/refactor.
- Do not work directly on `main`; create a feature branch from current HomeClaw `main` before implementation.

- [ ] **Step 4: Implement POST initialize and session routing**
